# Installing over an existing config

If you already have your own `~/.config/hypr`, `~/.config/ghostty`,
`~/.config/nvim`, GTK settings, or a Firefox profile, `install.sh` is written
so nothing of yours is silently deleted.

## The rule

Every file `install.sh` links, it links with the same helper
(`link()` in the script). Before it creates a symlink at a target path, it
checks what's already there:

- **Nothing there, or already the right symlink** — nothing to back up, it
  just links (or does nothing).
- **A real file or directory already at that path** — moved aside to
  `<path>.bak-YYYYmmdd-HHMMSS` (e.g.
  `~/.config/hypr/hyprland.lua.bak-20260925-143012`), then the symlink is
  created.

One consequence of this: the whole repo, `hyprland.lua` and the ghostty
config are symlinked wholesale (below), so editing any of them *through*
their `~/.config` link is editing a file this git clone tracks, not a private
copy. That's fine day to day, but it changes what a later `git pull` does —
see [Updating / re-running](updating.md).

This covers every one of: the whole repo → `~/.config/quickshell/rd-shell`,
`hypr/{hyprland.lua,hyprland-gui.lua,hypridle.conf,hyprlock.conf}` →
`~/.config/hypr/`, `hypr/dotfiles/ghostty` → `~/.config/ghostty`,
`scripts/{keybinds,mic-toggle,screenshot}.sh` → `~/.config/hypr/scripts/`,
and every file under `dotfiles/` → its matching `~/.config/<app>` path —
**including nvim now**: `init.lua`, `lua/{config,keymaps,commands,utils}.lua`
and `lazy-lock.json` are backed up and replaced the same as any other file
here, not left alone the way round-1 of this rice left them. See
[nvim](../dotfiles/nvim.md).

{% hint style="warning" %}
**Hyprland itself is the one config this doesn't gently merge with.** If your
`~/.config/hypr/hyprland.conf` looks like your own config rather than the
distro's autogenerated stub (checked against the literal
`AUTOGENERATED HYPRLAND CONFIG` marker, or byte-for-byte against
`/usr/share/hypr/hyprland.conf`), it's **copied** to
`hyprland.conf.bak-YYYYmmdd-HHMMSS` — the original is left in place
untouched, not deleted or moved. But `hyprland.lua` (linked next to it) is
what your session actually loads after your **next full Hyprland restart**
(logout/login, or `uwsm stop` + relaunch) — **not** a plain `hyprctl
reload`, which keeps reading the old `hyprland.conf` until that full
restart happens. This note is also repeated in the end-of-run Summary so
it's not easy to miss. If `hyprland.conf` was your real config and you want
to keep using it instead, just don't log back into Hyprland after the
install — `hyprland.conf` is still sitting there, unmodified, doing what it
always did.
{% endhint %}

## Files handled differently

A few files aren't simple symlinks, because they're real per-machine config
the script only edits in place — these use their own backup naming instead of
the generic one above:

| File | What happens | Backup |
|---|---|---|
| `~/.config/gtk-3.0/gtk.css`, `gtk-4.0/gtk.css` | one `@import` line appended if missing; rest of the file untouched | `gtk.css.bak-YYYYmmdd-HHMMSS` (copy, not move) only if the import line was missing |
| `~/.config/btop/btop.conf` | copied from `dotfiles/btop/btop.conf` only if absent; if present, only its `color_theme` line is patched (or appended) — never symlinked, since btop rewrites this file on its own exit; see [btop](../dotfiles/btop.md) | `btop.conf.bak-YYYYmmdd-HHMMSS`, only when an existing `color_theme` line had to be changed |
| `~/.config/cava/config` | copied from `dotfiles/cava/config` only if absent — matugen rewrites the whole file on every wallpaper switch anyway; see [cava](../dotfiles/cava.md) | none — nothing existing is ever touched |
| `/usr/share/pipewire/pipewire.conf.d/iriunaudio.conf` | one `nofail` flag patched in, only if the file exists and Iriun's package put it there | `iriunaudio.conf.bak` (via `sed -i.bak`, root-owned) |
| `<firefox profile>/chrome/userChrome.css`, `userContent.css` | overwritten with a two-line import stub, unless already exactly that stub | `<file>.bak-YYYYmmdd-HHMMSS` if something else was there |
| `~/.config/hypr/hyprland.conf` | copied to its backup, left in place and unused — **not** loaded once you're on `hyprland.lua` (see the warning above) | `hyprland.conf.bak-YYYYmmdd-HHMMSS`, only if it looked like your own config rather than the distro's stub |
| `~/.config/environment.d/terminal.conf`, `~/.config/xdg-terminals.list` | only written if absent | none needed (never overwrites) |
| `~/.bashrc` | one `eval "$(starship init bash)"` block appended, only if `starship init bash` isn't already there and `starship` is installed (or gets installed by this run); rest of the file untouched | `.bashrc.bak-YYYYmmdd-HHMMSS` (copy), only if the block had to be added and the file already existed |

Nothing else under your `$HOME` is touched. In particular, `~/.config/hypr`
keeps whatever else lives there (HyprMod's state, generated lock colours,
anything you put there yourself) — only the named files inside it are
linked or backed up.

## Rolling back

Every backup above sits right next to the file it replaced, with the same
name plus a `.bak-...` (or `.bak`) suffix, so reverting one piece is:

```bash
mv ~/.config/hypr/hyprland.lua.bak-20260925-143012 ~/.config/hypr/hyprland.lua
```

For a symlinked path, `rm` the symlink first if the `mv` target already
exists as one. There's no single "undo everything" command — restore whichever
backups you want, file by file. See [Uninstall / revert](uninstall.md) for
undoing the parts of the install that aren't file links (masked notification
daemons, systemd services, gsettings, KDE config keys).
